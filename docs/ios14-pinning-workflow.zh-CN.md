# iOS 14.0.1 上的 WLoc MITM 流程

本文记录一次 iOS 14.0.1 设备上的操作顺序和停止条件，供研究自己的设备时参考。它不是通用的一键修复方案；其他系统版本、信任资产和数据库内容必须重新只读核对。本文不提供修改系统数据库的安装包，也不包含任何设备备份或抓包。

## 1. 先确认三件不同的事

- **证书固定规则**：`trustd` 使用的 `pinningrules.sqlite3` 可能包含针对 `gs-loc.apple.com` 和 `gs-loc-cn.apple.com` 的规则。它与根证书是否被系统信任是两个独立条件。
- **HTTPS 解密**：Shadowrocket 模块需要启用，两个域名需要出现在 MITM hostname 中，Shadowrocket 根证书需要在系统中完全信任。
- **脚本语法**：原 WLoc 脚本含有 iOS 14.0.1 的 JavaScript 引擎不能解析的私有类字段。证书错误消失后若仍得到 404，应继续核对脚本是否运行。此仓库的 [`wloc-ios14.module`](../modules/wloc-ios14.module) 指向为较早 iOS 14 构建的脚本。

## 2. 获取只读基线

在自己的设备上通过 TrollStore 运行只读检查工具，先找出实际的数据库路径、表结构和目标规则。此次 iOS 14.0.1 设备的数据库位于 `/Library/Keychains/pinningrules.sqlite3`；不能直接套用 iOS 15 工具使用的路径，也不能仅凭“信任资产版本”推断规则一定存在。

目标规则按 **`policyName=AppleIssued`、`domainSuffix=apple.com`、`labelRegex=^gs-loc$|^gs-loc-cn$`** 三项共同识别。先确认恰好只有一行，并记录只读检查得到的结构、行数与该行内容。`rowid` 和总行数只用于核对本机状态，不应当作其他设备的固定值。找不到唯一目标、数据库结构不同、文件不是普通文件，或存在未处理的 SQLite WAL、SHM、journal 文件时，停止修改。

## 3. 在任何写入前完成备份

用 SQLite backup API 从只读连接生成独立副本，检查备份与源数据库的完整性、结构及目标行。把副本另存到电脑，核对两份文件的 SHA-256，并保留原件。备份或校验失败时停止；不要直接复制一个正在写入的数据库作为唯一备份。

## 4. 仅在本机核对通过后修改

需要设备所有者明确同意。工具应在受限的 SQLite 事务中再次比较实时数据库与备份，按上述三项条件及本次确认的行标识只删除**一行**。提交前检查删除数量恰为一，其他规则、管理表和结构与备份一致；任何检查不符则回滚。提交后关闭连接，再只读打开数据库独立核验。不要在检查或提交失败时自动重启、恢复或抹除设备。

此次设备完成单行删除后，重启前仍出现证书错误；重启后该证书错误消失。这与 `trustd` 缓存需要刷新相符，但单凭这一现象不能证明定位改写已经成功。

## 5. 分开验证脚本与定位效果

重启后使用本仓库的 iOS 14 模块，检查 Shadowrocket 的模块、MITM 域名和根证书信任状态。访问 `https://gs-loc.apple.com/wloc-settings/save?action=query` 时，只有脚本实际拦截请求才会返回 WLoc 的 JSON；Apple 原站的 404 不能当作设置成功。然后再观察真实的 `/clls/wloc` 请求及定位结果。

目前已验证的是单行数据库修改、重启后的证书错误变化，以及兼容脚本在模拟 Shadowrocket 环境中的设置请求响应。完整的真机定位改写效果仍需单独验证。

## 边界

删除这条规则不会把信任资产降级，也不会阻止 Apple 后续更新。`allowOTAPKIUpdates=false` 描述文件和 DNS/Shadowrocket 拦截规则属于另外的设置。整个流程不需要监管、恢复出厂设置或抹除设备；安装 TrollStore 和修改数据库本身仍会改变设备状态。
